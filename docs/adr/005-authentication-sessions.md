# ADR-005: Аутентификация — серверные сессии в cookie

- **Статус:** Принято
- **Дата:** 2026-11-09

## Контекст

Нужна аутентификация по email и паролю с подтверждением email и сбросом пароля ([requirements.md](../requirements.md) FR-1–FR-4). Требования безопасности (§6.1): секреты не утекают через XSS, нет CSRF, нельзя перебором выяснить, какие email зарегистрированы, сессии отзываются при выходе и смене пароля.

Архитектура ([ADR-001](001-system-topology.md)): один backend (NestJS) с одной БД; браузер общается с одним доменом, Next.js проксирует `/api/*` в NestJS через `rewrites` (сверено с документацией Next.js 16).

## Варианты

### JWT (access + refresh)

- ➕ Проверка подписи без обращения к БД.
- ➖ Отзыв требует короткого access-токена, ротации refresh-токенов и/или чёрного списка — то есть снова БД.
- ➖ В `localStorage` уязвим к XSS; в httpOnly cookie нуждается в той же CSRF-защите, что и сессии.
- ➖ Главное преимущество (проверка без общей БД) не нужно системе с одним backend.

### Готовая библиотека или провайдер (Better Auth, Clerk, Auth0)

- ➕ Меньше кода, проверенные решения.
- ➖ Механика скрыта; цель проекта — понять её. Внешний провайдер — дополнительная зависимость и стоимость.

### Серверные сессии

- ➕ Простой и мгновенный отзыв, минимум движущихся частей.
- ➖ Запрос к БД на каждый аутентифицированный запрос (индекс по первичному ключу — пренебрежимо на нашем масштабе).

## Решение

**Серверные сессии** на стандартных примитивах, без собственной криптографии.

- **Пароли:** Argon2id с параметрами по рекомендации OWASP Password Storage Cheat Sheet; параметры хранятся в строке хэша, что позволяет повышать их и перехэшировать при входе.
- **Токен сессии:** 32 байта из криптостойкого генератора, передаётся в cookie. В БД хранится только SHA-256 хэш токена.
- **Cookie:** `__Host-session; HttpOnly; Secure; SameSite=Lax; Path=/`. Имя и `Secure` настраиваются через окружение на случай проблем в локальной разработке.
- **Срок жизни:** скользящий — 30 дней с последней активности, абсолютный максимум — 90 дней с входа. Обновление `last_seen_at` не чаще раза в час, чтобы не писать в БД на каждый запрос.
- **Вход:** создаётся новая сессия (новый токен) — защита от фиксации сессии.
- **Отзыв:** выход удаляет сессию; смена и сброс пароля удаляют все сессии пользователя.
- **CSRF:** `SameSite=Lax` + проверка заголовка `Origin` для изменяющих методов (POST, PUT, PATCH, DELETE).
- **Токены из писем** (подтверждение email — 24 ч, сброс пароля — 1 ч): хранятся хэшем, одноразовость — условным UPDATE `WHERE used_at IS NULL AND expires_at > now()`.
- **Защита от перебора аккаунтов:** одинаковые ответы регистрации и восстановления пароля для существующих и новых email; единое сообщение об ошибке входа; вычисление хэша пароля даже при отсутствии пользователя (одинаковое время ответа).
- **Rate limiting:** `@nestjs/throttler` с хранением в памяти — для входа, регистрации, восстановления пароля и создания броней.
- **SSR:** серверные компоненты Next.js вызывают API напрямую (внутренний адрес), пробрасывая заголовок `Cookie` пользователя.
- **Авторизация** (права на ресурс) — не в guard, а в сервисах: запросы ограничиваются владельцем, чужой ресурс → 404.

## Последствия

- Новые таблицы `sessions` и `auth_tokens` ([data-model.md](../architecture/data-model.md)).
- Фоновая уборка истёкших сессий и токенов (вместе с обработчиком outbox).
- Хранение rate limit в памяти корректно только при **одном экземпляре** backend. Переход к нескольким экземплярам потребует общего хранилища (например, Redis) — это зафиксированное условие пересмотра.
- Next.js не обрабатывает аутентификацию сам: он только передаёт cookie. Источник истины о сессии — API.
- Прототип на этапе 4 проверяет работу `__Host-` cookie через rewrites на `http://localhost`.
- Вход через Google (FR-6, Later) добавится как ещё один способ создать ту же сессию.
