# ADR-007: Контракты API, ошибки и валидация

- **Статус:** Принято
- **Дата:** 2026-11-09

## Контекст

`web` и `api` — отдельно деплоящиеся приложения ([ADR-001](001-system-topology.md)), связанные HTTP-контрактом. Требования: документация API в OpenAPI (requirements §6.4), ошибки без утечки внутренних деталей (§6.1), понятная обработка конфликтов бронирования ([ADR-003](003-double-booking-protection.md)). Типы на frontend не должны расходиться с API.

Документация сверена 2026-11-09 (Context7: nestjs-zod, openapi-typescript / openapi-fetch).

## Варианты

### Валидация на границе

- **class-validator + class-transformer** (по умолчанию в NestJS): классы с декораторами; тип, проверка и OpenAPI описываются частично раздельно.
- **Zod + nestjs-zod**: одна схема даёт проверку в рантайме, TypeScript-тип и OpenAPI; знакома по frontend.

### Типы для frontend

- **Вручную** — расходятся с API.
- **Общий пакет с Zod-схемами** — схемы переиспользуются в формах, но web зависит от кода api, граница ADR-001 размывается.
- **OpenAPI как контракт** — web зависит от описания API, а не от его кода; документация и контракт — один артефакт; нужен шаг генерации и проверка в CI.

### Формат ошибок

- **Собственный формат** — нужно придумывать и документировать.
- **RFC 9457 Problem Details** — стандарт, поддерживается инструментами (в том числе типизация ошибок в openapi-fetch).

## Решение

- REST; ресурсы текущего пользователя под `/me`; переходы статуса брони — action-эндпоинты; без версии в URL при правиле обратной совместимости на один деплой.
- Ошибки — **RFC 9457 Problem Details** с расширениями `code`, `requestId`, `errors`. Доменные ошибки переводятся в HTTP в одном глобальном exception filter.
- Валидация формы — **Zod + nestjs-zod**; бизнес-правила — домен; инварианты — БД.
- Контракт — **OpenAPI 3.1**, генерируемый из Zod-схем; frontend использует **openapi-typescript** + **openapi-fetch**. `openapi.json` коммитится, CI проверяет его актуальность.

Подробности — [api.md](../architecture/api.md).

## Последствия

- Изменение контракта всегда видно в diff PR (`openapi.json` и сгенерированные типы).
- Схемы ответов явные: случайная утечка полей (например, `passwordHash`) не проходит.
- Зависимость от nestjs-zod (сторонняя интеграция): версии закрепляются, `cleanupOpenApiDoc` обязателен при генерации документа.
- Формы на frontend имеют собственную лёгкую валидацию для UX, которая может быть строже или мягче API, но не заменяет его.
- Idempotency-Key для создания брони отложен (см. api.md §6).
