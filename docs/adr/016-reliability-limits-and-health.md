# ADR-016: Тайм-ауты, лимиты и проверки здоровья

- **Статус:** Принято
- **Дата:** 2026-11-13

## Контекст

Модель угроз ([security.md](../architecture/security.md), A10) отметила, что у API нет ни тайм-аутов, ни лимитов. Опыт на работающем процессе показал больше:

- **База зависла** (`docker pause`: сеть теряет пакеты, сервер перегружен) — запросы висят без ограничения: у `pg.Pool` нет тайм-аута получения соединения. Запросы копятся, держат сокеты и память.
- **База перезапустилась** (`docker stop`: обновление, переключение на реплику) — **процесс API падает целиком**. Простаивающие соединения получают от сервера `57P01`, `pg.Pool` сообщает об этом событием `error`, а необработанное событие `error` в Node.js завершает процесс.
- `/health` при упавшей базе отвечал `500`, а не `503`: фильтр превращал любой 5xx `HttpException` во внутреннюю ошибку.
- Медленный клиент мог держать соединение 60–90 с до получения заголовков (slowloris); тело запроса — до 100 КБ.
- API слушал все сетевые интерфейсы: из локальной сети он был доступен в обход прокси web.

## Решение

### База данных: ждать ограниченно, отказывать быстро

- `connectionTimeoutMillis` (`DB_CONNECT_TIMEOUT_MS`, 2 с) — сколько запрос ждёт соединения из пула.
- `statement_timeout` (`DB_STATEMENT_TIMEOUT_MS`, 5 с) — PostgreSQL сам отменяет долгий запрос и освобождает его работу. Лучше клиентского тайм-аута: сервер не продолжает работу, ответ на которую никто не ждёт.
- `query_timeout` = `statement_timeout` + 1 с — страховка на клиенте: замороженный сервер ничего отменить не может, без неё запрос в уже открытое соединение висел бы вечно (проверено мутацией).
- `pool.on('error')` пишет предупреждение в лог. Пул сам выбрасывает сломанное соединение и открывает новое при следующем запросе.
- `application_name = slotly-api` — наши соединения видны в `pg_stat_activity`.
- Ошибки «база недоступна» (`isDatabaseUnavailable` в `pg-errors.ts`) — коды PostgreSQL `08xxx`, `57P01–57P03`, `53300`, `57014`, ошибки сокета, сообщения `pg` о тайм-аутах — глобальный фильтр превращает в `503 SERVICE_UNAVAILABLE` с `Retry-After: 30` и пишет одну строку уровня `warn`, а не стек на каждый запрос. Это сбой инфраструктуры, а не доменная ошибка, поэтому репозитории его не переводят.

### Проверки здоровья: два разных вопроса

| Маршрут             | Вопрос                         | Ходит в базу | Если не `200`                    |
| ------------------- | ------------------------------ | ------------ | -------------------------------- |
| `GET /health/live`  | процесс жив и отвечает по HTTP | нет          | оркестратор **перезапускает**    |
| `GET /health/ready` | можно принимать запросы        | да           | балансировщик **не шлёт трафик** |

Liveness проверяет только то, что чинится перезапуском. Если бы он проверял базу, минутный сбой базы перезапускал бы все экземпляры по кругу: перезапуск базу не вернёт, а при её возвращении все экземпляры одновременно открывают соединения. Readiness, наоборот, сам вернётся в `200`, когда база ответит. Тайм-аут проверки readiness в оркестраторе должен быть больше худшего времени ответа `503` (до 6 с при значениях по умолчанию) — этап 9.

### HTTP-сервер

- `headersTimeout` 10 с, `requestTimeout` 30 с (по умолчанию в Node 60 и 300 с).
- `connectionsCheckingInterval` 1 с. Node проверяет оба тайм-аута раз в этот интервал, по умолчанию раз в 30 с: медленный клиент держал соединение 25–40 с вместо 10 (измерено). Это опция `http.createServer()`, а сервер создаёт Nest; Node читает свойство при `listen()`, поэтому оно выставляется до запуска. Свойства нет в типах `Server` — если Node перестанет его читать, упадёт тест slowloris.
- `keepAliveTimeout` — по умолчанию (5 с): прокси Next.js — клиент Node, он закрывает простаивающее соединение на 1 с раньше подсказки сервера. За балансировщиком значение должно быть больше его idle timeout — этап 9.
- Лимит тела 32 КБ для JSON и форм (наши тела — единицы КБ; Express по умолчанию 100 КБ, а разбор большого JSON блокирует цикл событий). Ошибки middleware Express (`413` от body-parser) теперь отдаются как Problem Details: фильтр распознаёт ошибки `http-errors` с `expose: true` и статусом 4xx — раньше это был `500`.

### Сетевой интерфейс

`HOST` — IP-адрес, по умолчанию `127.0.0.1`: API доступен только web-серверу на той же машине. Имя хоста не принимается: `localhost` может разрешиться в `::1` или в `127.0.0.1`, и сервер слушал бы не тот адрес, к которому обращается web. В контейнере (этап 9) — `0.0.0.0`. `API_INTERNAL_URL` в примерах — `http://127.0.0.1:4000`.

## Последствия

- Сбой базы — быстрые `503` вместо зависших запросов и падения процесса; после её возвращения сервис восстанавливается без перезапуска. Проверено `reliability.e2e.test.ts` на настоящей PostgreSQL (`pg_terminate_backend`, `docker pause`) и мутациями каждой защиты.
- Запрос дольше 5 с в базе отменяется. Если появится законно долгий запрос (отчёт, миграция данных), ему нужен свой `SET LOCAL statement_timeout` в транзакции, а не общее увеличение.
- Соединение транзакции, прерванной `query_timeout`, Drizzle возвращает в пул без пометки об ошибке; оно очищается, когда сервер ответит. Тест проверяет, что сервис после этого восстанавливается.
- Web-сервер Next.js по-прежнему слушает все интерфейсы — его размещение решается на этапе 9.
