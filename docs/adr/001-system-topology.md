# ADR-001: Топология системы

- **Статус:** Принято
- **Дата:** 2026-11-09

## Контекст

Нужно определить исполняемые части системы и их связи. Ядро продукта — бизнес-правила бронирования и защита от двойных броней ([requirements.md](../requirements.md) FR-51, §4). Масштаб — сотни специалистов, один разработчик. Проект учебный: одна из целей — освоить проектирование backend на NestJS.

## Варианты

### A. Только Next.js (Route Handlers / Server Actions + ORM)

- ➕ Один деплой, нет межсервисной аутентификации и CORS, минимум кода.
- ➖ Бизнес-логика внутри UI-фреймворка, её легко размазать по компонентам и экшенам.
- ➖ Нет явного API для других клиентов; слабее изоляция для тестов.

### B. Next.js (web) + NestJS REST API (api) + PostgreSQL

- ➕ Явная граница: бизнес-правила, права доступа и данные — в одном сервисе.
- ➕ Backend тестируется и развивается независимо; DI и модули NestJS поддерживают слоистую структуру.
- ➖ Два деплоя; контракт API нужно синхронизировать между приложениями.
- ➖ Аутентификация сложнее (cookie между двумя сервисами).

### C. Микросервисы

- ➖ Распределённые транзакции, сетевые отказы, оркестрация — без выгоды на нашем масштабе.

## Решение

Вариант **B**. Backend — **модульный монолит**: один процесс, одна БД, модули с явными границами (предварительно: `auth`, `users`, `specialists`, `scheduling`, `bookings`, `notifications`).

Честная мотивация: для продукта такого масштаба вариант A тоже был бы приемлем. B выбран, потому что (1) центральные бизнес-правила выигрывают от изолированного, отдельно тестируемого слоя и (2) проект ставит целью освоение backend-архитектуры.

## Последствия

- **Правило границы:** у `web` нет доступа к БД. Все данные и бизнес-правила — только через API.
- Бизнес-правила не дублируются во frontend; клиентская валидация — только для UX, источник истины — API.
- Нужен механизм синхронизации контракта API (решение 6 этапа архитектуры).
- Браузер общается с одним доменом; предварительно — прокси `/api/*` из Next.js в NestJS для first-party cookie (окончательно — в ADR по аутентификации).
- Если модуль в будущем потребует независимого масштабирования, явные границы модулей позволят выделить его в сервис.
