# ADR-013: Стратегия тестирования и браузерные e2e на Playwright

- **Статус:** Принято
- **Дата:** 2026-11-12

## Контекст

К концу этапа 5 в проекте три уровня тестов: unit (домен), интеграционные (репозитории на настоящем PostgreSQL) и e2e API (HTTP → весь `AppModule` → БД). Они не проверяют то, что ломается **между** приложениями: прокси Next.js → API, cookie `__Host-` в браузере, SSR и гидратацию, часовой пояс браузера, ссылку из настоящего письма. Все такие проверки до сих пор делались вручную, и именно на них находились ошибки в интерфейсе.

Нужно решить, чем и как проверять систему целиком, не делая тесты медленными и «мигающими».

## Варианты

### Только ручная проверка в браузере

- ➖ Не повторяется перед каждым слиянием, зависит от внимательности, не войдёт в CI.

### Компонентные тесты web (React Testing Library) с моком API

- ➕ Быстро.
- ➖ Мок API — это то, чего у нас как раз нет в проверках: прокси, cookie, контракт. Проверяли бы сами себя.

### Браузерные e2e на Playwright против настоящего стека

- ➕ Проверяют то, что видит пользователь: настоящие web, API, БД и письма. Эмуляция часового пояса и локали, несколько независимых контекстов браузера в одном тесте (клиент и специалист), трассировка падений.
- ➖ Медленнее остальных уровней; нужна изоляция данных и окружения.

Cypress не рассматривался подробно: Playwright поддерживает несколько контекстов в одном тесте, эмуляцию `timezoneId` и работает без отдельного сервиса записи.

## Решение

**Playwright, пакет `e2e/`** в монорепозитории — тесты проверяют всю систему, а не одно приложение.

1. **Изолированный стек на прогон.** Playwright (`webServer`) пересоздаёт базу `slotly_e2e` миграциями, собирает и запускает API (порт 4100) и web (порт 3100, `next build` с адресом тестового API в отдельный каталог `.next-e2e`). Dev-серверы и dev-данные не затрагиваются. Письма — через Mailpit из `compose.yaml`.
2. **Одна база на прогон, уникальные данные на тест.** Тесты идут параллельно; очистка базы перед каждым тестом стирала бы данные соседних (рассмотрено в срезе 6.1). Каждый тест создаёт свои email и slug и не полагается на общее состояние. База на каждого воркера отвергнута: потребовала бы по паре серверов API и web на воркер.
3. **Через интерфейс — только проверяемый сценарий.** Подготовка (специалист с расписанием и услугой) — через публичный HTTP API, включая подтверждение email по ссылке из настоящего письма.
4. **Никаких тестовых переключателей в приложении.** Rate limit работает по-настоящему: каждый контекст браузера получает свой `X-Forwarded-For`, Next.js передаёт его в API, API доверяет прокси на loopback ([ADR-005](005-authentication-sessions.md)).
5. **Доказательства падения** — трассировка, скриншот и видео сохраняются только для упавших тестов.
6. Браузерные тесты не входят в `pnpm test` (им нужны браузеры и Docker): отдельная команда `pnpm test:e2e`. В CI — этап 8.

Уровни и их ответственность описаны в [testing.md](../architecture/testing.md).

## Последствия

- Конфигурация web получила `NEXT_DIST_DIR` (каталог сборки), по умолчанию `.next`.
- Один раз на машине: `pnpm --filter @slotly/e2e exec playwright install chromium`.
- Прогон начинается со сборки API и web — около минуты; для локальной отладки серверы можно переиспользовать (`E2E_REUSE_SERVERS=1`).
- Тест, которому нужен общий счётчик или пустая таблица, в этой схеме не пишется — такие проверки остаются на уровне e2e API с собственной базой в Testcontainers.
