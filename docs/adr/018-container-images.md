# ADR-018: Docker-образы и один образ для всех окружений

- **Статус:** Принято
- **Дата:** 2026-11-13

## Контекст

Этап 9 будет разворачивать api и web на хостинге; нужен артефакт, который можно проверить в CI и отправить в любое окружение без изменений. Препятствие нашлось в ADR-005: Next.js записывает адрес API из `rewrites()` в сборку (`routes-manifest.json`), поэтому образ web годился бы только для одного окружения.

## Варианты

### A. Свой образ на окружение (`--build-arg API_INTERNAL_URL=…`)

Ничего не меняется в коде. Но в production уходит не тот образ, который проверяли на staging, а пересобранный: базовый образ по тегу мог переехать (digest `node:24-alpine` и `node:24.21.0-alpine` уже различались при подготовке этого ADR), системные пакеты, кэш, опечатка в аргументе. Lock-файл закрепляет только npm-зависимости.

### B. Адрес API читается при запуске

Проксирование `/api/*` переезжает из `rewrites()` в `proxy.ts`: `NextResponse.rewrite` на `API_INTERNAL_URL` из окружения. Оба механизма проходят через один код сервера Next.js: `X-Forwarded-*` выставляются до переписывания, тело, метод и cookie передаются так же.

## Решение

**Вариант B.** Один образ — один digest — проверяется в CI, публикуется и отправляется в любое окружение; provenance связывает его с коммитом и workflow.

### web

- `proxy.ts`: `/api/*` → `apiTarget()` (`shared/api/api-target.ts`, юнит-тесты: префикс снимается, хост не покидается при `//`, `@`, `%2F`); CSP — только для страниц.
- `next.config.ts` больше не знает адреса API (`loadBuildEnv`); `server-client.ts` читает окружение при вызове, а не при импорте — сборка импортирует модули страниц и адреса не имеет.
- `output: 'standalone'`, `outputFileTracingRoot` — корень монорепозитория (зависимости pnpm лежат в корневом `node_modules`).
- Проверено: сборка без `API_INTERNAL_URL`, запуск с ним; все e2e; в образе — страница, вход с неверным паролем (401 от API через прокси), POST без `Origin` → 403.

### Образы (`apps/api/Dockerfile`, `apps/web/Dockerfile`, контекст — корень репозитория)

- Базовый образ `node:24.21.0-alpine`, закреплён по digest (как actions по SHA); обновляет Dependabot (экосистема `docker`, без мажорных версий).
- Многоэтапная сборка: pnpm через corepack и все зависимости — на этапе сборки; в итоговом образе — `pnpm deploy --prod` (api: `dist`, `drizzle` из поля `files` и только production-зависимости) или standalone-сервер (web).
- Файлы принадлежат root, процесс работает от `node`: он не может изменить свой код.
- `HEALTHCHECK`: api — `/health/ready`, web — `/login` (здоровье самого web, не API).
- `.dockerignore`: ни `node_modules`, ни сборок, ни `.env` — секреты не попадают даже на этап сборки.
- api: `HOST=0.0.0.0` (ADR-016). Размеры: api ~340 МБ, web ~300 МБ.

### Миграции — отдельный шаг

`node dist/migrate.js` (`db:migrate:deploy`) — тот же мигратор `drizzle-orm`, что в тестах, с той же служебной таблицей; `drizzle-kit` (dev-зависимость) в образ не попадает. Конфигурация — только `DATABASE_URL` (`loadMigrationConfig`). Не при старте приложения: несколько экземпляров соревновались бы за изменение схемы, а обслуживающему процессу не нужны права на DDL.

### CI

- `images` (на каждом PR, права только на чтение): сборка обоих образов и smoke-проверка `scripts/smoke-images.sh` через `compose.yaml` + `compose.images.yaml` — стек здоров, миграции прошли, процессы не от root, страница с nonce-CSP, `/api/health/ready` через web, заголовки API сохранены, POST без `Origin` → 403. Поведение проверяют e2e; здесь — упаковка.
- `publish` (только push в `main`, после всех проверок) — единственная задача с правами на запись. Загружает **те же** образы из артефакта `images` (`docker save`), а не пересобирает; публикует в GHCR с тегами `sha-<коммит>` и `main`; `actions/attest` создаёт подписанное provenance (SLSA) для каждого digest.
- `compose.images.yaml` пригоден и локально: запустить ровно то, что уйдёт в production.

## Последствия

- Деплой (этап 9) берёт образ по `sha-<коммит>` или digest и задаёт окружение при запуске; пересборка на окружение не нужна.
- Каждый запрос `/api/*` проходит через `proxy.ts` — ещё одна причина держать его быстрым (без обращений к API).
- Проверка provenance перед деплоем (`gh attestation verify`) — этап 9.
- Сканирование образов на уязвимые системные пакеты не входит в срез: `pnpm audit:prod` покрывает npm-зависимости, базовый образ обновляет Dependabot. Решить на этапе 9.
- Мутация проверена: образ api без `USER node` → smoke `api runs as root`.
