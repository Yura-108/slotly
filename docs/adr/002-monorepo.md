# ADR-002: Монорепозиторий

- **Статус:** Принято
- **Дата:** 2026-11-09

## Контекст

Согласно [ADR-001](001-system-topology.md) система состоит из двух приложений (`web`, `api`), которые связаны контрактом API. Разработку ведёт один человек; изменение функциональности обычно затрагивает оба приложения.

## Варианты

### Монорепозиторий (pnpm workspaces)

- ➕ Атомарные изменения: frontend, backend и контракт — в одном PR.
- ➕ Общие конфигурации (TypeScript, ESLint, Prettier) и один CI.
- ➖ Сложнее начальная настройка; CI должен избегать лишних пересборок.

### Два репозитория

- ➕ Полная независимость приложений и их версий.
- ➖ Изменение контракта требует двух согласованных PR; дублирование конфигураций.

## Решение

Монорепозиторий на **pnpm workspaces**:

```
apps/
  web/        Next.js
  api/        NestJS
packages/     общий код (состав — по решению о контрактах API)
docs/
```

Нужен ли инструмент оркестрации задач (например, Turborepo), решаем на этапе 4 (организация разработки).

## Последствия

- Одна история изменений и один CI-пайплайн с проверками для затронутых приложений.
- В `packages/` попадает только то, что действительно используется обоими приложениями; бизнес-логика backend туда не выносится.
- Деплой приложений остаётся независимым, несмотря на общий репозиторий.
