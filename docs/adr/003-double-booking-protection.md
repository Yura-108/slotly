# ADR-003: Защита от двойного бронирования

- **Статус:** Принято 2026-11-09 по результатам прототипа (см. «Результаты прототипа»).
- **Дата:** 2026-11-09

## Контекст

У специалиста не может быть двух пересекающихся активных броней, в том числе при одновременных запросах ([requirements.md](../requirements.md) FR-51). Слоты не хранятся в БД, а вычисляются (FR-41), поэтому нет строки «слот», которую можно заблокировать. Длительности услуг разные, значит, брони пересекаются произвольными интервалами.

Дополнительно: `pending`-бронь занимает время до истечения срока `min(создание + 24 ч, начало брони)` (FR-54). В ограничениях PostgreSQL нельзя использовать `now()`: ограничение обязано давать одинаковый результат для одной и той же строки в любой момент времени.

## Варианты

### 1. Проверка в коде: SELECT пересечений, затем INSERT

- ➖ Гонка: два запроса одновременно видят «свободно» и оба вставляют бронь. Не выполняет FR-51.

### 2. Блокировка строки специалиста (`SELECT ... FOR UPDATE`) перед проверкой и вставкой

- ➕ Работает в любой ORM, сериализует бронирования к одному специалисту.
- ➖ Корректность держится на дисциплине: любой новый путь записи, забывший взять блокировку, снова открывает гонку.

### 3. Уровень изоляции SERIALIZABLE

- ➕ Корректность обеспечивает БД.
- ➖ Нужны повторы при ошибках сериализации; сложнее рассуждать о поведении.

### 4. Таблица слотов с уникальным индексом

- ➖ Не подходит к вычисляемым слотам и разной длительности услуг.

### 5. Exclusion constraint PostgreSQL по интервалу времени

- ➕ Инвариант гарантирует БД при любом пути записи и любой конкурентности.
- ➖ Специфично для PostgreSQL; нужно расширение `btree_gist`; ORM может не поддерживать такое ограничение в схеме — тогда его пишут SQL-миграцией.

## Решение

Вариант **5**:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (
    specialist_id WITH =,
    tstzrange(start_at, end_at, '[)') WITH &&
  )
  WHERE (status IN ('pending', 'confirmed'));
```

- Интервал полуоткрытый `[)`: брони 10:00–11:00 и 11:00–12:00 не конфликтуют.
- Условие зависит только от `status`, без `now()`.

**Истечение `pending`** — в два уровня:

1. **При создании брони**, в той же транзакции перед `INSERT`, переводим в `expired` просроченные `pending`, пересекающиеся с запрошенным интервалом:

   ```sql
   UPDATE bookings SET status = 'expired'
   WHERE specialist_id = $1
     AND status = 'pending'
     AND expires_at <= now()
     AND tstzrange(start_at, end_at, '[)') && tstzrange($2, $3, '[)');
   ```

   Затем `INSERT`. Нарушение ограничения (SQLSTATE `23P01`) → ответ 409 Conflict.

2. **Фоновая задача** периодически переводит остальные просроченные `pending` в `expired` и ставит письма клиентам. Она нужна для уведомлений и аккуратности данных, **но не для корректности**.

**Эффективный статус** вычисляется в одном месте доменного кода: `pending` с `expires_at <= now()` считается `expired` везде — при вычислении слотов, в списках, при попытке подтверждения.

## Результаты прототипа (2026-11-09)

Реализация: миграция `apps/api/drizzle/0001_bookings_no_overlap.sql`, `BookingsRepository`, интеграционные тесты `bookings.repository.int.test.ts` на PostgreSQL 18 в Testcontainers.

Подтверждено:

- Из 20 одновременных попыток забронировать одно время успешна ровно одна, в БД ровно одна бронь — во всех прогонах.
- Соседние интервалы (`[)`) не конфликтуют, частичное пересечение — конфликтует; отменённая бронь время не занимает.
- Просроченная `pending` истекает в транзакции создания, и её время бронируется; до срока — конфликт.
- Условный UPDATE: из двух одновременных переходов статуса применяется ровно один; истёкшую `pending` подтвердить нельзя.
- `CHECK` «срок только у pending» работает на уровне БД.

Обнаружено и исправлено:

- **Deadlock `40P01` при одновременных вставках.** Транзакции, вставляющие пересекающиеся интервалы, ждут незакоммиченные строки друг друга в индексе ограничения; PostgreSQL разрывает цикл через `deadlock_timeout` (1 с). Инвариант не нарушался, но часть отказов приходила как `40P01` вместо `23P01`, а задержки накапливались (прогон теста — 19 с). Решение: в начале транзакции брони — **транзакционная advisory-блокировка на специалиста** `pg_advisory_xact_lock(hashtextextended(specialist_id, 0))`. Попытки к одному специалисту выстраиваются в очередь, отказ всегда `23P01`, прогон — ~0,1 с на раунд. Advisory-блокировка не обращается к таблице `specialist_profiles` (владение таблицами, [ADR-006](006-backend-layers-and-modules.md)); коллизии хэша приводят лишь к лишнему ожиданию.
- **Время — параметр**, а не `now()` в SQL: истечение сравнивается с `now`, переданным из use case, — так же, как вычисляется эффективный статус в домене (единое время для обоих, детерминированные тесты).

Итоговый порядок в транзакции создания брони: `lockSpecialistSchedule` → `expireOverduePendingOverlapping` → `insert` (`23P01` → `BookingConflictError`).

Роли механизмов: exclusion constraint — **корректность** (держит инвариант при любом пути записи, даже если блокировку забудут); advisory-блокировка — **предсказуемое поведение** при конкуренции.

## Последствия

- Двойное бронирование невозможно даже при ошибке в коде приложения.
- В таблице `bookings` есть `expires_at` (только для `pending`).
- Код создания брони обязан обрабатывать `23P01` как штатный конфликт, а не как 500.
- Нужен интеграционный тест с настоящим PostgreSQL на одновременное бронирование (unit-тест с моком БД этот инвариант не проверит).
- Миграция с ограничением написана на SQL вручную (custom-миграция drizzle-kit).
- Бронирования к одному специалисту сериализуются; на масштабе продукта (единицы броней в минуту на специалиста) это не ограничение.
