# ADR-010: Окружение и процесс разработки

- **Статус:** Принято; инструмент проверки границ модулей уточнён в [ADR-011](011-architecture-checks-and-git-hooks.md)
- **Дата:** 2026-11-09

## Контекст

Начинается этап 4 — организация разработки. Нужно зафиксировать версии платформы, способ локального запуска, инструменты качества кода и Git workflow. Разработку ведёт один человек с AI-ассистентом; процесс должен быть близок к командному, но без лишних церемоний.

Проверено 2026-11-09: Node.js v26 — Active LTS с 2026-10-28, v24 — maintenance LTS до 2028-04-30 (nodejs/Release schedule); PostgreSQL 18 — последняя стабильная мажорная версия (postgresql.org/support/versioning).

## Решения

### Версии

- **Node.js 24** (maintenance LTS). v26 вышла в LTS две недели назад; нативные модули (`argon2`) могут отставать с готовыми бинарниками. Переход на v26 — запланированная задача в начале 2027 года.
- **pnpm 12** — версия закреплена в поле `packageManager` корневого `package.json`; точные версии зависимостей (`saveExact`). Скрипты установки зависимостей запрещены по умолчанию и разрешаются явно (`allowBuilds`).
- **TypeScript 6.0.x**, а не 7. TypeScript 7 (июнь 2026) — нативный компилятор на Go, а typescript-eslint поддерживает TypeScript `>=4.8.4 <6.1.0` (проверено 2026-11-09). Переход на 7 — когда его поддержат typescript-eslint, NestJS CLI и Next.js.
- **NestJS 11**, а не 12. NestJS 12 (август 2026, ESM) пока не поддерживается nestjs-zod (peer `@nestjs/common ^10 || ^11` в версии 5.6.0 от 2026-11-08), на котором построен [ADR-007](007-api-contracts-errors-validation.md). Ветка 11 активно получает исправления. Миграция на 12 — отдельная задача, когда nestjs-zod объявит поддержку.
- **Минимальный «возраст» релиза.** pnpm 12 не устанавливает только что опубликованные версии (защита от скомпрометированных релизов). Если нужная версия слишком свежая, берём предыдущий патч, а не добавляем исключение в `minimumReleaseAgeExclude`.
- **PostgreSQL 18** — в том числе встроенная `uuidv7()` для первичных ключей (закрывает открытый вопрос [data-model.md](../architecture/data-model.md)). Поддержка версии хостингом — критерий выбора на этапе 9.

### Локальный запуск

- Инфраструктура — **Docker Compose**: PostgreSQL 18 (порт хоста **55432**: 5432 и 5433 на машине разработчика заняты локальными установками PostgreSQL) и Mailpit (перехват писем с веб-интерфейсом).
- `apps/api` и `apps/web` запускаются **на хосте**: быстрый hot reload, простая отладка, нет проблем с отслеживанием файлов в контейнерах на Windows.
- Docker-образы приложений появляются на этапах 8–9 и используются в CI и production; паритет окружений обеспечивает именно образ.

### Качество кода

- **ESLint (flat config) + Prettier**: официальные конфигурации Next.js и NestJS, плагины для проверки границ модулей ([ADR-006](006-backend-layers-and-modules.md)).
- **TypeScript strict** во всех пакетах.
- **Тесты — Vitest** (быстрый, нативный ESM, тот же инструмент в web); декораторы NestJS компилируются через SWC (`unplugin-swc`).
- **Интеграционные тесты — на настоящем PostgreSQL через Testcontainers**: чистая БД на каждый прогон, одинаково локально и в CI, без влияния на данные разработки.

### Git workflow

- **GitHub Flow**: короткие ветки от `main`, слияние через Pull Request, **squash merge**.
- **Conventional Commits**: проверяется заголовок PR в CI (при squash он становится коммитом в `main`).
- **pre-commit**: только быстрые проверки изменённых файлов (форматирование, линт, поиск секретов — [ADR-015](015-dependencies-and-secrets.md)). Типы и тесты — в CI.
- Репозиторий — приватный на GitHub.

## Варианты, которые не выбраны

- Node 26 сейчас — риск несовместимости нативных модулей при минимальной выгоде.
- Приложения в Docker при разработке — медленнее цикл правки, сложнее отладка; паритет с production даёт образ из CI.
- Biome — один быстрый инструмент, но беднее экосистема плагинов, правила границ модулей потребовали бы отдельного инструмента.
- Хук на каждый коммит (commitlint) — избыточен при squash merge.

## Последствия

- Требуется установка pnpm на машине разработчика.
- Переход на Node 26 — отдельная задача с прогоном CI.
- Переход на NestJS 12 (с переходом api на ESM) — отдельная задача после поддержки в nestjs-zod.
- В `main` попадает только проверенный код через PR; прямые коммиты в `main` — только на этапе первоначальной настройки до создания GitHub-репозитория.
