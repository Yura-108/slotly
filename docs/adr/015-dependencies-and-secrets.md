# ADR-015: Уязвимые зависимости и поиск секретов

- **Статус:** Принято
- **Дата:** 2026-11-12

## Контекст

`pnpm audit` нашёл high-уязвимость `multer` в production-зависимостях (через `@nestjs/platform-express`) и 8 уведомлений в dev-зависимостях. Аудит нигде не запускался автоматически, о новых уязвимостях никто бы не узнал, а секрет, случайно добавленный в коммит, ничто бы не остановило ([security.md](../architecture/security.md), A03 и A04).

`multer` в Slotly недостижим: ни один маршрут не принимает файлы. Это не повод его оставлять: проверка аудита полезна, только пока она зелёная, а записка «к нам не относится» забудется, когда появится загрузка аватара.

## Решение

### Правило разбора уведомления

1. **Есть исправление, совместимое с родителем** — обновляем родителя (`@nestjs/*` 11.2.8 → 11.2.9 приносит `multer` 2.5.0). Пакеты одного семейства обновляются вместе.
2. **Родитель закрепил точную уязвимую версию, исправление в той же мажорной** — точечный `overrides` в `pnpm-workspace.yaml` с комментарием, когда его убрать. Сейчас один: `typed-rest-client>qs` 6.15.1 → 6.17.1 (Stryker; четыре DoS-уведомления; `typed-rest-client` 3.x сам требует `^6.16.1`).
3. **Исправление только в новой мажорной или его нет** — риск принимается и записывается ниже с причиной. Принятые риски допустимы только в dev-зависимостях: в production так нельзя, там аудит должен быть чистым.

Принятые (dev-инструменты; в production-образ не попадают; разбирают наш код, а не ввод злоумышленника):

| Пакет            | Через                                     | Почему не исправлено                                                                      |
| ---------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------- |
| `esbuild` 0.18   | `drizzle-kit` → `@esbuild-kit` (заброшен) | Уязвим dev-сервер esbuild, drizzle-kit его не поднимает; ждём drizzle-kit без esbuild-kit |
| `glob` 10/13     | `testcontainers` → `archiver`             | Исправление только в `glob` 14 — мажорная, несовместимая с `archiver`                     |
| `minimatch` 9/10 | ESLint-плагины, Stryker                   | Исправление только в 11 — мажорная                                                        |
| `deepmerge` 4.3  | `@nestjs/cli` → `fork-ts-checker`         | Исправленной версии нет                                                                   |

Dependabot предложит обновление, как только родитель его выпустит; при этом запись удаляется.

### Проверки

- `pnpm audit:prod` (`pnpm audit --prod`) — любая уязвимость в production-зависимостях роняет проверку; в CI — с этапа 8. Dev-зависимости в неё не входят: неисправимое уведомление сделало бы её вечно красной.
- **Dependabot** (`.github/dependabot.yml`): обновления безопасности — сразу; версии — раз в неделю для npm (pnpm), `docker-compose` и `github-actions`. Минорные и патчи — одним PR из всех папок workspace. Мажорные версии npm и Docker Compose плановыми обновлениями не предлагаются: это миграции (`@types/node` привязан к Node 24; TypeScript, Nest, PostgreSQL меняют код или данные), их место — ROADMAP. Без этого правила первый запуск открыл 14 PR, мажорные — по одному на каждую папку workspace. Документация GitHub противоречива в том, действует ли `ignore` на обновления безопасности; страховка — `pnpm audit:prod`, который падает при уязвимости в production независимо от Dependabot. `cooldown` 3 дня — то же, что `minimumReleaseAge` pnpm: свежий релиз ещё может оказаться скомпрометированным.

### Секреты

- **secretlint** с `preset-recommend` в pre-commit на **всех** staged-файлах. Он вызывается из `.husky/pre-commit`, а не из lint-staged: у приложений свои конфиги lint-staged, и задачу пришлось бы повторять в каждом. `--no-glob` — пути Next.js вроде `[slug]` остаются буквальными. `pnpm secrets:check` проверяет всё рабочее дерево.
- **История git** проверена однократно: каждая версия каждого файла из всех веток (615 blob'ов, 33 коммита) — тем же secretlint, с контрольным секретом, чтобы убедиться, что проверка срабатывает. Секретов нет, `.env` в историю не попадал. Проверка истории в CI (gitleaks) — этап 8.
- GitHub secret scanning с push protection для приватного репозитория платный (GitHub Secret Protection); при переходе в публичный — включить.

## Варианты, которые не выбраны

- **`overrides` для всего подряд** — подмена версии в обход родителя ставит сочетание, которое никто не тестировал; мажорные подмены ломают API.
- **`auditConfig.ignoreGhsas`** — список исключений тот же самый, но без причины рядом с проблемой; `--prod` делает его ненужным.
- **gitleaks в pre-commit** — бинарник на Go, `pnpm install` его не ставит; у каждого разработчика хук молча не работал бы.

## Последствия

- Production-зависимости без известных уязвимостей, и это проверяется.
- Секрет не пройдёт в коммит незамеченным (если хук не обойти через `--no-verify`, что запрещено; страховка — CI на этапе 8).
- Принятые риски видны и имеют условие пересмотра; каждый `override` — временный.
- Поток PR от Dependabot — регулярная работа; без CI (этап 8) каждый проверяется вручную.
