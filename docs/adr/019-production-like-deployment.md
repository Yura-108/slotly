# ADR-019: Production-подобная среда и процедура деплоя

- **Статус:** Принято
- **Дата:** 2026-11-13

## Контекст

Этап 9 выполняется локально, без публичного хостинга и домена (решение пользователя: бюджет). Чтобы эксплуатация была настоящей, а не воображаемой, нужна среда, устроенная как production: образы из реестра, проверенные по provenance, HTTPS за обратным прокси, закрытые внутренние сервисы, деплой и откат одной командой. Отличия от сервера — нет интернета и реальной почты.

## Решение

### Стек `deploy/compose.yaml` (проект `slotly-prod`)

```
клиент ──HTTPS :8443──► caddy ─(edge)─► web ─(internal)─► api ──► postgres
```

- **Caddy 2.11.9** — единственный сервис с опубликованным портом. HTTPS от локального центра сертификации (`local_certs`); корневой сертификат экспортируется в `deploy/caddy-root.crt` — им пользуется smoke-проверка, им можно разрешить браузеру доверять. `admin off`.
- **Сеть `internal`** (`internal: true`, подсеть `172.30.20.0/24`): web, api, PostgreSQL, Mailpit. Маршрута наружу нет — проверено: `fetch('https://example.com')` из api обрывается.
- **Цепочка `X-Forwarded-For`.** Caddy не доверяет заголовку клиента и записывает в него адрес соединения; web передаёт его без изменений; api доверяет только подсети `internal` (`TRUSTED_PROXY`). Проверено живьём: 11 входов подряд с разными подделанными адресами — 10 × `401`, 11-й `429`. Мутация (Caddy доверяет клиенту и api доверяет всем частным адресам) — 11 × `401`, лимит обойдён. Защита двойная: при поломке только Caddy адрес клиента всё равно не принимается — его записал не web.
- **`keepalive 4s` у Caddy к web.** Простаивающее соединение закрывает клиент раньше сервера (Node в web — 5 с), иначе Caddy иногда отправлял бы запрос в закрываемое соединение (`502`). То же правило для балансировщика хостинга — ADR-016.
- **Две роли PostgreSQL** (`deploy/postgres/init-roles.sh`, первый старт тома): `slotly_owner` владеет базой и схемой — от него `migrate`; `slotly_app` — только `SELECT/INSERT/UPDATE/DELETE` через `ALTER DEFAULT PRIVILEGES` — от него api. Проверено: `drop table bookings` → `must be owner`, `create table` → `permission denied for schema public`. SQL-инъекция в API не изменит схему. Пароли передаются в psql переменными (`:'name'`), не подставляются в текст запроса.
- **Секреты** — `deploy/.env` (в git не попадает, шаблон `deploy/.env.example`); текущий релиз — `deploy/.env.release`, пишет `deploy.sh`.
- **Mailpit** вместо почтового сервиса (нет домена), UI — только `127.0.0.1:8026`.
- Образы Caddy и PostgreSQL закреплены по digest; Dependabot следит за `deploy/compose.yaml`.

### Деплой `deploy/deploy.sh <sha>`

1. `gh attestation verify` для обоих образов: подпись нашего `ci.yml`, ветка `refs/heads/main`, раннеры GitHub (`--deny-self-hosted-runners`). Иначе — отказ (мутация `--source-ref` другой ветки → `exit 1`). Реестр читается с пустым конфигом Docker — анонимно, как на сервере; пакеты GHCR публичные.
2. `docker pull`, запуск **по digest**.
3. База, затем `docker compose run --rm migrate` от `slotly_owner`.
4. `up -d --wait` api, web, caddy — ждёт health checks.
5. `deploy/smoke.sh` через HTTPS-вход: страница с nonce-CSP и HSTS, `/api/health/ready`, POST без `Origin` → `403`, опубликован только Caddy (и Mailpit на `127.0.0.1`).
6. Запись в `deploy/releases.log` — откат: `deploy.sh <предыдущий sha>`.

### Миграции: expand/contract

Откат кода не откатывает схему. Поэтому каждая миграция совместима с кодом **предыдущего** релиза: переименование колонки — это три релиза (добавить новую и писать в обе → читать новую → удалить старую, когда откат дальше уже не нужен), удаление — только того, что прошлый релиз уже не использует. Миграции 0000–0007 только добавляли — правило не нарушено; теперь оно обязательно.

### Сканирование образов

Задача `images` в CI сканирует оба образа Trivy 0.76.2 (бинарник по sha256, как gitleaks): падает на `HIGH/CRITICAL` с исправлением; без исправления — в отчёте, не блокирует (правило ADR-015).

Первый прогон нашёл 3 HIGH в Alpine 3.24.2 (`musl`, `zlib`) и 10 HIGH в npm, который поставляется в базовом образе (`undici`, `tar`, `brace-expansion`, `ip-address`). Решение: базовый образ `node:24.22.3-alpine` (Alpine 3.24.4 с исправлениями) и удаление npm, npx, corepack и yarn из итогового образа — приложение запускается одним `node`. Размер не уменьшился: удаление в новом слое скрывает файлы, но не убирает базовые слои; в контейнере их нет, сканер проверяет итоговую файловую систему.

### Swagger UI

Не подключён: API отдаёт только сгенерированный `openapi.json` в репозитории. Отложенный вопрос «`/docs` в production» снят; если UI появится, тест матрицы доступа потребует решения о его публичности.

## Последствия

- Релиз — одна команда с проверкой происхождения; откат — та же команда.
- Найдено при проверке: `curl` для Windows (Schannel) требует данных об отзыве сертификата, которых у локального центра нет — smoke использует `--ssl-revoke-best-effort` только там; сертификат по-прежнему проверяется (с чужим корневым сертификатом — отказ). `docker compose port` для непубликуемого порта печатает `invalid IP:0` с кодом 0 — проверка публикаций читает `docker ps`.
- Сохранённые в Docker Desktop учётные данные `ghcr.io` подставляются даже при пустом конфиге CLI; устаревшие дают `denied` на публичный образ — `docker logout ghcr.io`.
- На настоящем хостинге Caddy заменяет балансировщик платформы, `local_certs` — Let's Encrypt, Mailpit — почтовый сервис с доменом (срез 9.4).
