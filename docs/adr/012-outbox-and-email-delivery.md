# ADR-012: Outbox и доставка писем

- **Статус:** Принято
- **Дата:** 2026-11-10

## Контекст

Письма — побочный эффект изменений данных: регистрация, сброс пароля, а со среза 6 — брони (FR-60–62). Требования:

- письмо не уходит об изменении, которое откатилось, и не теряется, если изменение сохранено;
- сбой почтового сервиса не ломает основную операцию, отправка повторяется (FR-62);
- модуль `notifications` не зависит от других модулей ([ADR-006](006-backend-layers-and-modules.md)): payload содержит всё нужное для письма.

Таблица `outbox_messages` уже описана в [data-model.md](../architecture/data-model.md); там же отложено «окончательное устройство обработчика». Фоновые задачи выполняются в процессе API с `FOR UPDATE SKIP LOCKED` ([backend.md](../architecture/backend.md) §4).

## Варианты

### Отправка письма прямо в сервисе

- ➖ До коммита — письмо о том, что может откатиться; после коммита — потеря письма при падении процесса; синхронно — медленный почтовый сервис замедляет или ломает запрос.

### Очередь-брокер (Redis/BullMQ, RabbitMQ)

- ➕ Готовые повторы и мониторинг.
- ➖ Запись в брокер не входит в транзакцию PostgreSQL — та же проблема атомарности. Новая инфраструктура без необходимости.

### Transactional outbox в PostgreSQL

- ➕ Изменение и «намерение отправить» сохраняются атомарно.
- ➖ Свой обработчик: аренда, повторы, остановка.

### Транспорт: SDK провайдера или SMTP

- SDK/HTTP API — богаче (идемпотентность, вебхуки), но привязывает код к провайдеру, а локально нужен второй путь.
- SMTP — поддерживают все транзакционные сервисы и Mailpit; один путь кода везде.

## Решение

- **Transactional outbox.** Сервис пишет сообщение через `NotificationsService.enqueue(tx, message)` в той же транзакции, что и изменение данных.
- **Типы сообщений — Zod-схемы** (дискриминированное объединение по `type`). Payload проверяется при записи (ошибка в коде видна сразу) и при обработке. Совместимость: новые поля — только необязательные; несовместимое изменение — новый `type`. Сообщения, записанные старой версией, должны обрабатываться новой.
- **Обработчик — цикл опроса в процессе API** (интервал `OUTBOX_POLL_INTERVAL_MS`, по умолчанию 5 с; `0` выключает цикл — так в тестах). Запуски не накладываются; при остановке приложения цикл дожидается текущей пачки. Без `@nestjs/schedule`: эти две гарантии нужны явно.
- **Аренда вместо долгой транзакции.** Короткая транзакция выбирает до 10 сообщений `status = 'pending' AND next_attempt_at <= now … FOR UPDATE SKIP LOCKED` и сдвигает `next_attempt_at` на 5 минут вперёд, увеличивая `attempts`. Отправка — вне транзакции. Успех → `sent`; ошибка → повтор по расписанию. Если процесс упал во время отправки, аренда истекает и сообщение берётся снова. Несколько экземпляров API не возьмут одно сообщение.
- **Повторы:** пауза `2^(attempts−1)` минут (1, 2, 4, …), не более 8 попыток (около 4 часов). Затем `failed` и запись уровня `error`.
- **Гарантия доставки — «как минимум один раз».** Падение между приёмом письма SMTP-сервером и записью `sent` даёт повторную отправку. «Ровно один раз» между двумя системами без общей транзакции недостижимо; дубль редкий и безвредный. `Message-ID` письма стабилен (`<id сообщения outbox>@slotly`), поэтому часть почтовых клиентов склеивает дубли.
- **Секреты в payload.** Ссылка с токеном (подтверждение email, сброс пароля) хранится в поле `link` только до отправки: при `sent` и `failed` поле удаляется из payload. Payload не логируется. Сгенерировать токен в момент отправки нельзя — `notifications` писал бы в таблицу `auth_tokens` модуля `auth`.
- **Транспорт — SMTP через nodemailer.** `SMTP_URL` (секрет): локально Mailpit (`smtp://localhost:1025`), в production — SMTP почтового сервиса (выбор — этап 9). `EMAIL_FROM` — адрес отправителя. Заменяет предварительную переменную `EMAIL_PROVIDER_API_KEY`.
- **Шаблоны — функции TypeScript** (текст и простой HTML на русском), без шаблонизатора.

## Последствия

- Любая новая отправка письма — новый тип сообщения со схемой, шаблоном и тестом.
- Письмо уходит с задержкой до интервала опроса (секунды).
- Возможен редкий дубль письма; получатель должен его переносить (для уведомлений это так).
- `failed`-сообщения видны в логах; алерт на них — этап 9.
- Отправленные сообщения накапливаются; уборка (срез 8): `sent` хранятся 30 дней, `failed` — 90, `pending` не удаляются ([backend.md](../architecture/backend.md) §4).
- Остаточный риск перебора аккаунтов: `password-reset/request` для существующего email пишет в БД, для несуществующего — нет; разница — единицы миллисекунд. Принят: rate limit (10 запросов в минуту на IP) не даёт набрать статистику; полное выравнивание потребовало бы фоновой обработки самого запроса.
