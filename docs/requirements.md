# Требования

> Статус: утверждены 2026-11-09 (черновик от 2026-11-06). Изменения — только через явное решение с записью в ROADMAP.
> Основа: [discovery.md](discovery.md).

## 1. Глоссарий

| Термин | Значение |
| --- | --- |
| Пользователь | Зарегистрированный аккаунт. Любой пользователь может быть клиентом |
| Специалист | Пользователь с включённым профилем специалиста |
| Услуга | То, на что записываются: название, длительность, описание. Принадлежит специалисту |
| Правило расписания | Рабочий интервал по дню недели в локальном времени специалиста, например «пн 10:00–18:00» |
| Выходной | Дата, в которую специалист не принимает записи (весь день) |
| Слот | Вычисляемый интервал, на который можно записаться. **Не хранится** в БД |
| Бронь | Факт записи клиента на услугу специалиста на конкретный интервал. Хранится в UTC |
| Активная бронь | Бронь, которая занимает время: `pending` (не истёкшая) или `confirmed` |

## 2. Роли и права доступа

Права определяются **владением ресурсом**, а не только ролью.

| Действие | Гость | Пользователь (клиент) | Специалист (владелец) |
| --- | --- | --- | --- |
| Смотреть публичную страницу специалиста, услуги и свободные слоты | ✅ | ✅ | ✅ |
| Создать бронь | ❌ (нужен вход) | ✅ (не к самому себе) | — |
| Смотреть бронь | ❌ | только свои | только брони к себе |
| Отменить бронь | ❌ | свою, до дедлайна отмены | любую к себе, в любой момент |
| Подтвердить / отклонить бронь | ❌ | ❌ | брони к себе в статусе `pending` |
| Управлять услугами, расписанием, выходными, настройками | ❌ | ❌ | только своими |
| Включить профиль специалиста | ❌ | ✅ | — |

Чужой ресурс для API выглядит как несуществующий (404), чтобы не раскрывать факт его существования.

## 4. Бизнес-процессы

### 4.1 Жизненный цикл брони

```
 создание (ручной режим)        создание (авто-режим)
          │                              │
          ▼          подтвердить         ▼
     ┌─────────┐ ─────────────────▶ ┌───────────┐
     │ pending │                    │ confirmed │
     └─────────┘                    └───────────┘
       │  │  │                            │
       │  │  └── отмена ──┐     ┌─ отмена ┘
       │  │               ▼     ▼
       │  │            ┌───────────┐
       │  │            │ cancelled │
       │  │            └───────────┘
       │  └─ отклонить ─▶ rejected
       └─── срок истёк ─▶ expired
```

| Из | В | Кто / когда |
| --- | --- | --- |
| — | `pending` | клиент, у специалиста ручной режим |
| — | `confirmed` | клиент, у специалиста авто-режим |
| `pending` | `confirmed` | специалист, до истечения срока |
| `pending` | `rejected` | специалист |
| `pending` | `cancelled` | клиент или специалист |
| `pending` | `expired` | система, по сроку |
| `confirmed` | `cancelled` | специалист — всегда; клиент — до дедлайна отмены |

- Конечные статусы: `rejected`, `cancelled`, `expired`. Из них переходов нет.
- Любой переход, не показанный на схеме, — ошибка бизнес-правила.
- **Срок истечения `pending`**: `min(создание + 24 ч, начало брони)`. Истёкшая `pending`-бронь не занимает время, даже если её статус ещё физически не обновлён в БД.
- «Прошедшая» бронь — не статус, а вычисляемое свойство (`end < now`).

### 4.2 Создание брони

1. Клиент выбирает услугу и слот на странице специалиста.
2. Сервер повторно проверяет: услуга активна, слот укладывается в расписание, не выходной, соблюдены минимальное время и горизонт, клиент ≠ специалист, email подтверждён, лимит `pending` не превышен.
3. Сервер атомарно создаёт бронь; если время уже занято — ответ «конфликт», клиенту предлагается выбрать другой слот.
4. Отправляются уведомления (асинхронно относительно ответа клиенту).

## 5. Нестандартные ситуации

| Ситуация | Ожидаемое поведение |
| --- | --- |
| Два клиента одновременно бронируют одно время | Успешна ровно одна бронь, второй — конфликт (409) |
| Слот стал недоступен между просмотром и отправкой | Конфликт (409), понятное сообщение, обновление списка слотов |
| Специалист изменил расписание, а на старое время есть брони | Брони остаются в силе |
| Специалист сменил длительность услуги | Существующие брони сохраняют свою длительность |
| Специалист сменил часовой пояс | Брони (UTC) не меняются; правила расписания трактуются в новом поясе |
| Переход на летнее/зимнее время | Несуществующее локальное время (весенний сдвиг) — слот пропускается; повторяющееся (осенний сдвиг) — без дублей слотов |
| Клиент пытается отменить после дедлайна | Отказ с объяснением; отменить может только специалист |
| Попытка забронировать у себя | Отказ |
| Подтверждение уже истёкшей/отменённой брони | Отказ (переход недопустим) |
| Сбой почтового сервиса | Бронь создана, письмо будет отправлено повторно |
| Падение запроса посреди операции | Нет «полусозданных» данных: операция атомарна |

## 6. Нефункциональные требования

### 6.1 Безопасность

- Пароли хранятся только в виде стойкого хэша; секреты — только в переменных окружения, не в репозитории.
- Все проверки прав — на сервере; frontend не является границей безопасности.
- Валидация всех входных данных на сервере.
- Ошибки не раскрывают внутренние детали (стек, SQL).
- Ограничение частоты запросов (rate limiting) для входа, регистрации, восстановления пароля и создания броней.
- Защита от перебора email: ответы регистрации/восстановления не раскрывают, существует ли аккаунт.
- Защита от распространённых веб-уязвимостей (OWASP Top 10): XSS, CSRF (в зависимости от схемы сессий), инъекции.
- Токены из писем (подтверждение, сброс пароля) — одноразовые и с ограниченным сроком.

### 6.2 Производительность и масштаб

- Ориентир масштаба: сотни специалистов, десятки тысяч броней. Горизонтальное масштабирование не требуется.
- Вычисление слотов на горизонт до 60 дней — p95 < 300 мс на сервере.
- Остальные API-запросы — p95 < 200 мс при обычной нагрузке.

### 6.3 Надёжность и данные

- Целостность данных обеспечивается на уровне БД (ограничения), а не только кодом приложения.
- Миграции схемы версионируются и применяются автоматически при развёртывании.
- Резервное копирование БД (по возможностям хостинга).
- Health check для сервиса и БД.
- Структурированные логи; ошибки сервера отслеживаются.

### 6.4 Сопровождаемость

- Строгий TypeScript на frontend и backend.
- Автоматические тесты на бизнес-правила брони, авторизацию и конкурентное бронирование.
- Документация API в OpenAPI.

### 6.5 UX и доступность

- Адаптивный интерфейс (мобильные устройства в приоритете для клиентской части).
- Базовая доступность: семантическая разметка, навигация с клавиатуры, контраст.
- Язык интерфейса: русский. Мультиязычность (i18n) — вне MVP.

## 7. Ограничения

- Небольшой бюджет инфраструктуры: бесплатные или недорогие тарифы.
- Стек: Next.js, NestJS, PostgreSQL, Docker; разработку ведёт один человек с AI-ассистентом.
- Отправка email — через внешний транзакционный сервис (выбор на этапе архитектуры).
