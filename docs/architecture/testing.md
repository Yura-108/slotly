# Тестирование

> Статус: утверждено 2026-11-12. Решение: [ADR-013](../adr/013-testing-strategy.md).

## 1. Уровни

| Уровень        | Где                             | Что гарантирует                                                                                                      | Что подменяется                                                                 |
| -------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Unit           | `apps/*/src/**/*.test.ts`       | правила в изоляции: слоты и переход на летнее время, машина состояний, политики, шаблоны писем, форматирование       | ничего — домен чистый, время передаётся параметром                              |
| Интеграционные | `apps/api/src/**/*.int.test.ts` | SQL, ограничения БД, гонки (exclusion constraint, compare-and-set, блокировки)                                       | ничего — PostgreSQL в Testcontainers                                            |
| E2E API        | `apps/api/src/**/*.e2e.test.ts` | контракт HTTP, права и IDOR, транзакции, письма в outbox, фоновые задачи                                             | только источник конфигурации; SMTP — недоступный адрес или Mailpit в контейнере |
| E2E браузер    | `e2e/tests/*.spec.ts`           | то, что видит пользователь: прокси Next.js → API, cookie, SSR и гидратация, пояс браузера, ссылки из настоящих писем | ничего                                                                          |

Правило выбора уровня: проверка идёт на **самый нижний уровень, где ошибка видна**. Расчёт слотов при переводе часов — unit; «двое одновременно бронируют одно время» — интеграционный и e2e API; «время показано в поясе клиента» и «после входа специалист попадает на заявки» — браузер.

## 2. Что не мокаем

- **Базу данных.** Корректность при конкуренции обеспечивает PostgreSQL ([ADR-003](../adr/003-double-booking-protection.md)); мок не воспроизведёт ни блокировки, ни ограничения.
- **API в браузерных тестах.** Мок проверял бы сам себя, а не прокси, cookie и контракт.
- **Часы в домене не подменяются** — `now` передаётся аргументом. Фейковые таймеры — только для движка фоновых задач.

## 3. Браузерные e2e (`e2e/`)

Запуск: `pnpm test:e2e` (нужны `docker compose up -d --wait` и один раз `pnpm --filter @slotly/e2e exec playwright install chromium`). Отчёт: `pnpm test:e2e:report` (Playwright установлен только в пакете `e2e/`, поэтому его подсказка `pnpm exec playwright show-report` из корня не работает).

- **Стек на прогон:** база `slotly_e2e` пересоздаётся миграциями; API на `:4100`, web на `:3100` (сборка в `.next-e2e`); письма — Mailpit `:8025`. Dev-серверы на 3000/4000 не мешают.
- **Изоляция данных:** одна база на прогон, тесты параллельны; каждый тест создаёт свои email и slug (`uniqueEmail`, `uniqueSlug`). Нельзя: утверждать про общее количество строк, полагаться на порядок тестов, чистить таблицы.
- **Свой адрес клиента:** у каждого контекста браузера и API-клиента свой `X-Forwarded-For` — rate limit настоящий, но не общий для всех тестов.
- **Подготовка — через API** (`support/api.ts`: `verifiedPerson` регистрирует, подтверждает email по ссылке из письма и входит). Через интерфейс — только проверяемый сценарий.
- **Письма:** `support/mailpit.ts` ждёт письмо по адресу и теме; `linkTo` достаёт ссылку на страницу приложения.
- **Поиск элементов** — по ролям и подписям (`getByRole`, `getByLabel`), как их видит пользователь и экранный диктор; не по CSS-классам.
- **Ожидание** — только через автоожидающие проверки (`expect(...).toBeVisible()`, `expect.poll`), никаких фиксированных пауз (правило линтера `eslint-plugin-playwright`).
- **Вход без формы** (`signIn`): сессия из API кладётся в контекст той же cookie `__Host-session`, что ставит сервер. Форму входа проверяет свой тест; при её поломке падает он один, а не все сценарии. Cookie задаётся для `https://localhost`: DevTools ставит `Secure`-cookie только для https-адреса, а Chromium отправляет её и на `http://localhost` (безопасный контекст).
- **Подготовка специалиста** (`specialist()`): Берлин, 09:00–17:00 каждый день, услуга 60 минут; `freeSlots()` — свободные слоты из API для сверки с экраном.
- **После перехода — дождаться новой страницы** (заголовок или URL), прежде чем искать поле: на старой странице может быть поле с той же подписью, и автоожидание найдёт его.
- **Не зависеть от времени запуска.** Ожидаемое вычисляется из данных API (времена слотов в поясе браузера), а не константами; первый свободный слот может быть и через час, и через три дня — проверки допускают оба исхода.
- **Несколько людей в одном тесте** — отдельные контексты (`personContext`): у каждого свои cookie, адрес и, при необходимости, часовой пояс.
- При падении сохраняются трассировка, скриншот и видео: `pnpm --filter @slotly/e2e exec playwright show-trace <путь>`.

### Сценарии

| Файл                       | Что проверяет                                                                                                                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth.spec.ts`             | регистрация → письмо → подтверждение → вход → `/start`; ссылка подтверждения одноразовая; сброс пароля по письму (старый пароль больше не подходит)                                   |
| `specialist-setup.spec.ts` | специалист через интерфейс: профиль → услуга → неделя → у посетителя появились слоты                                                                                                  |
| `booking.spec.ts`          | запись → «Ждут ответа» → подтверждение → у клиента «Подтверждена» и письмо; два клиента на один слот; слоты на часах клиента во Владивостоке; отклонение с причиной и отмена клиентом |

Проверка на нестабильность: `pnpm --filter @slotly/e2e test:e2e --repeat-each=3`.

## 4. Мутационная проверка

Тест, который не может упасть, ничего не проверяет. Для каждой ключевой защиты (проверка `Origin`, условие владельца, блокировки, compare-and-set, учёт истечения) её временно убирали и смотрели, что падает ровно нужный тест; находки — в журнале обучения. Автоматизация (Stryker для домена) — срез 6.3.
