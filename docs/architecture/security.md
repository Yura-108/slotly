# Модель угроз и безопасность

Что мы защищаем, от кого, где проходят границы доверия и какая защита закрывает каждую угрозу. Сверено с [OWASP Top 10:2025](https://top10.owasp.org/2025). Документ меняется вместе с кодом: новая граница доверия, новый публичный маршрут или новый секрет — правка здесь.

## 1. Активы

| Актив                     | Почему ценен                                                                   |
| ------------------------- | ------------------------------------------------------------------------------ |
| Учётные записи и пароли   | Пароль часто повторяется на других сайтах — утечка вредит за пределами Slotly. |
| Сессии                    | Cookie сессии = вход без пароля.                                               |
| Персональные данные       | Имя, email, часовой пояс; у брони — с кем и когда встреча, причина отказа.     |
| Брони и время специалиста | Чужая отмена, подтверждение или «забивание» слотов — прямой ущерб работе.      |
| Одноразовые токены писем  | Ссылка из письма подтверждает email или меняет пароль.                         |

## 2. Нарушители

| Кто                    | Что может                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| Анонимный посетитель   | Любые HTTP-запросы к публичным маршрутам, перебор паролей и адресов, массовая регистрация. |
| Пользователь-чужак     | Вошёл честно, но подставляет чужие `id` (IDOR), шлёт недопустимые переходы статуса, гонки. |
| Чужой сайт (CSRF)      | Заставляет браузер жертвы отправить запрос к нам с её cookie.                              |
| Сканер почты / прокси  | Открывает ссылки из писем (GET) раньше человека.                                           |
| Читатель логов         | Доступ к логам или их копиям, но не к БД.                                                  |
| Поставщик зависимостей | Уязвимый или вредоносный пакет в `node_modules` (срез 7.3).                                |

## 3. Границы доверия

```
браузер ──HTTPS──▶ Next.js (web, прокси /api/*) ──▶ API (NestJS) ──▶ PostgreSQL
                                                     └──SMTP──▶ почтовый сервер ──▶ ящик пользователя
```

- **Браузер → web.** Всё от браузера — недоверенные данные. Web не обращается к БД и не принимает решений (правила 1–2 CLAUDE.md).
- **web → API.** Прокси передаёт cookie и `X-Forwarded-For`; API доверяет `X-Forwarded-For` только от прокси (`trust proxy`, ADR-005), иначе лимиты по IP обходились бы подменой заголовка.
- **API → PostgreSQL.** Только параметризованные запросы Drizzle; инварианты — ограничениями БД (правило 6).
- **API → почта.** Письмо уходит из outbox после фиксации транзакции; в нём только ссылка с одноразовым токеном.

## 5. Матрица доступа

`apps/api/src/infrastructure/http/access-matrix.e2e.test.ts` берёт **настоящую таблицу маршрутов** запущенного Express-приложения (не OpenAPI и не метаданные Nest) и для каждого маршрута проверяет:

1. Без cookie — `401 UNAUTHENTICATED`, кроме маршрутов из списка `PUBLIC_ROUTES`.
2. Множество маршрутов, ответивших не `401`, **в точности равно** `PUBLIC_ROUTES`. Список записан в тесте руками: если бы тест брал «публичность» из `@Public()`, маршрут, помеченный открытым по ошибке, был бы пропущен — тест согласился бы с ошибкой. Нужен независимый источник истины.
3. Любой изменяющий запрос (`POST`, `PUT`, `PATCH`, `DELETE`) без `Origin` или с чужим `Origin` — `403 ORIGIN_NOT_ALLOWED`, публичные маршруты тоже.

Добавить маршрут в `PUBLIC_ROUTES` — решение о безопасности, оно видно в ревью. Новый закрытый маршрут проверяется автоматически.

Проверка проверена мутациями: `@Public()` на `GET /me/bookings` → падает п. 2 (`+ "GET /me/bookings"`); `OriginGuard`, пропускающий запрос без `Origin`, → падает п. 3.

Публичные маршруты сейчас: `GET /health`; `POST /auth/register|login|logout|verify-email|password-reset/request|password-reset/confirm`; `GET /specialists/:slug`, `/specialists/:slug/services`, `/specialists/:slug/slots`.

## 6. Чего модель не покрывает

- Компрометация машины разработчика или сервера, физический доступ.
- DDoS на уровне сети — забота хостинга и CDN (этап 9); приложение защищается лимитами и тайм-аутами (7.4).
- Безопасность почтового ящика пользователя: доступ к ящику = возможность сбросить пароль. Это принятый риск входа по email.
