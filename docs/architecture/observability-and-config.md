# Логирование и конфигурация

> Статус: утверждено 2026-11-09. Решение: [ADR-008](../adr/008-logging-and-configuration.md).
> Мониторинг, отслеживание ошибок и сбор логов на хостинге — этап 9.

## 1. Логирование (apps/api)

**Инструмент:** nestjs-pino (pino + pino-http).

### Формат и вывод

- JSON-строки в stdout; файлы приложение не пишет — логи собирает платформа.
- Локально — читаемый вывод через `pino-pretty` (`LOG_FORMAT=pretty`).

### Корреляция

- `requestId`: генерируется на каждый запрос (`crypto.randomUUID`). Приём `X-Request-Id` от доверенного прокси (наш web) — когда появится web и настройка `TRUSTED_PROXY`.
- Присутствует в каждой строке лога запроса (AsyncLocalStorage), в заголовке ответа `X-Request-Id` и в Problem Details.
- Фоновые задачи: контекст — `outboxMessageId`, `attempt`, имя задачи.

### Уровни

| Уровень | Когда                                                                                                                                                                  |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `error` | ответы 5xx; сообщение outbox исчерпало попытки; сбой фоновой задачи                                                                                                    |
| `warn`  | повтор отправки outbox; сработал rate limit; отклонён `Origin`; медленный запрос (> 1 с)                                                                               |
| `info`  | одна строка на запрос (метод, маршрут-шаблон, статус, длительность, `userId`); бизнес-события (`booking.created`, `booking.cancelled` — с ID, без персональных данных) |
| `debug` | только локально                                                                                                                                                        |

### Чего не логируем

- Пароли, токены сессий и из писем, cookie, заголовок `Authorization` — `redact` в pino + тела запросов и ответов не логируются вообще.
- Персональные данные: в логах `userId`, а не email или имя.
- Полный URL с query-строкой для маршрутов с токенами — логируется шаблон маршрута.

## 2. Токены в ссылках из писем

Ссылка подтверждения email и сброса пароля передаёт токен во **фрагменте** URL: `https://<домен>/verify-email#token=...`.

| Канал утечки                                    | Почему фрагмент защищает                                     |
| ----------------------------------------------- | ------------------------------------------------------------ |
| Access-логи web-сервера, прокси, CDN            | фрагмент не отправляется на сервер                           |
| Заголовок `Referer` к сторонним ресурсам        | фрагмент не входит в Referer                                 |
| Адресная строка, история, синхронизация вкладок | страница сразу удаляет токен из URL (`history.replaceState`) |

Дополнительно: `Referrer-Policy: no-referrer` на этих страницах, токены одноразовые с коротким сроком (ADR-005) — это главная защита, если токен всё же утёк.

### Поток проверки

```
1. Клиент открывает ссылку     GET /verify-email           → web отдаёт страницу (токена в запросе нет)
2. JS на странице              читает location.hash, удаляет его из адресной строки
3. JS отправляет токен         POST /api/auth/verify-email  { token }  → API проверяет и гасит токен
4. Страница показывает результат
```

Побочный плюс: сканеры ссылок в почтовых сервисах открывают ссылки GET-запросом. Если бы токен гасился на GET, сканер мог бы израсходовать одноразовый токен до пользователя. Здесь GET ничего не меняет.

- **Сброс пароля:** токен отправляется только вместе с новым паролем из формы — сканер не может его использовать.
- **Подтверждение email:** POST отправляется автоматически при загрузке страницы. Сканер, выполняющий JavaScript, теоретически может подтвердить email вместо пользователя; ущерб минимален (адрес и так принадлежит получателю письма), поэтому кнопку подтверждения не добавляем.

## 3. Конфигурация

### Правила

1. Источник — переменные окружения. `.env` — только для локальной разработки (в `.gitignore`); `.env.example` со всеми ключами без секретов — в репозитории.
2. Проверка при старте Zod-схемой: при ошибке приложение не запускается и печатает список проблем.
3. Доступ только через типизированный `AppConfig`; чтение `process.env` вне модуля конфигурации запрещено правилом линтера.
4. Поведение задаётся явными параметрами, а не проверками `NODE_ENV` по коду.
5. Секреты: CI — GitHub Secrets; production — хранилище секретов хостинга.

### Переменные apps/api (предварительно)

| Переменная               | Назначение                                                                                                 |
| ------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `PORT`                   | порт HTTP                                                                                                  |
| `DATABASE_URL`           | подключение к PostgreSQL (секрет)                                                                          |
| `APP_ORIGIN`             | origin web-приложения: проверка `Origin`, ссылки в письмах                                                 |
| `SESSION_COOKIE_NAME`    | по умолчанию `__Host-session`; с префиксом `__Host-` требует `COOKIE_SECURE=true` (проверяется при старте) |
| `COOKIE_SECURE`          | по умолчанию `true`; Chromium принимает Secure на `http://localhost`                                       |
| `TRUSTED_PROXY`          | Express `trust proxy`: от каких адресов принимать `X-Forwarded-For` (по умолчанию `loopback`)              |
| `EMAIL_PROVIDER_API_KEY` | ключ почтового сервиса (секрет)                                                                            |
| `EMAIL_FROM`             | адрес отправителя                                                                                          |
| `LOG_LEVEL`              | `info` / `debug`                                                                                           |
| `LOG_FORMAT`             | `json` / `pretty`                                                                                          |

### Переменные apps/web (предварительно)

| Переменная            | Назначение                                                                   |
| --------------------- | ---------------------------------------------------------------------------- |
| `API_INTERNAL_URL`    | адрес API для rewrites и SSR — **только серверная**                          |
| `SESSION_COOKIE_NAME` | имя cookie сессии для оптимистичного редиректа в `proxy.ts`; совпадает с api |

Переменные web читаются только в `apps/web/src/shared/config` (и в `next.config.ts` через него); правило линтера запрещает `process.env` в остальном коде. Адрес в rewrites вычисляется при `next build` и фиксируется в сборке — смена `API_INTERNAL_URL` при запуске на него не влияет (решение для production — этап 9).

### Адрес клиента за прокси

Цепочка в production: балансировщик хостинга дописывает адрес клиента в `X-Forwarded-For` → Next.js передаёт заголовок без изменений и **свой адрес не добавляет** (проверено в срезе 1) → API видит соединение от Next.js. API доверяет заголовку, только если соединение пришло с адреса из `TRUSTED_PROXY`, и берёт крайний правый адрес: его записал балансировщик, клиент не может его подделать. Серверные компоненты web при запросах к API пробрасывают `X-Forwarded-For` входящего запроса, иначе все SSR-запросы попали бы в один лимит. Локально заголовка нет, и все запросы считаются от одного клиента — это нормально.

`NEXT_PUBLIC_*` встраиваются в бандл при сборке: они публичны и фиксируются в момент `build`. Используем их только для того, что действительно публично и одинаково для окружения сборки.
