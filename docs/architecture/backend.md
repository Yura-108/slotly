# Архитектура backend (apps/api)

> Статус: утверждена 2026-11-09. Решение: [ADR-006](../adr/006-backend-layers-and-modules.md).

## 1. Слои

```
controller      HTTP: маршруты, DTO, валидация входа, маппинг ответа.
   │            Бизнес-логики нет.
   ▼
service         Use case: оркестрация, транзакция, проверка прав,
(application)   вызов домена, запись в outbox.
   │      │
   ▼      ▼
domain        repository
чистые функции   Drizzle-запросы, условные UPDATE,
и типы, без      перевод кодов PostgreSQL в доменные ошибки
NestJS и БД
```

| Слой       | Можно                                                                                                              | Нельзя                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| controller | DTO, валидация, вызов одного сервиса, маппинг в ответ                                                              | вызывать репозиторий, принимать бизнес-решения                                     |
| service    | открывать транзакцию, вызывать домен и репозитории своего модуля, вызывать экспортированные сервисы других модулей | писать SQL, знать про HTTP (`Request`, статус-коды)                                |
| domain     | чистые функции, типы, доменные ошибки                                                                              | импортировать NestJS, Drizzle, `Date.now()` напрямую (время передаётся параметром) |
| repository | запросы к таблицам **своего** модуля, приём `tx`                                                                   | бизнес-правила, обращение к чужим таблицам                                         |

Правила:

- **Глубина слоёв соответствует сложности логики.** Domain-слой есть там, где есть правила: `bookings` (машина состояний, эффективный статус, расчёт слотов), `scheduling` (валидация интервалов), `auth` (сроки сессий). У CRUD-модулей (`services`, `users`) его нет.
- **Репозиторий — конкретный класс без интерфейса.** Проверяется интеграционными тестами на настоящем PostgreSQL.
- **Транзакцию открывает service** и явно передаёт `tx` в репозитории (и в сервис outbox).
- **Время — параметр.** Доменные функции получают `now` аргументом: расчёт слотов и истечения детерминирован и тестируется без подмены часов.

## 2. Модули и зависимости

```
auth ──────────┬──▶ users
               └──▶ notifications
specialists ──────▶ users
services ─────────▶ specialists
scheduling ───────▶ specialists
bookings ──────┬──▶ scheduling
               ├──▶ services
               ├──▶ specialists
               └──▶ notifications
notifications       (ни от кого не зависит)
infrastructure      (БД, конфигурация, логирование, health — используется всеми)
```

| Модуль        | Владеет таблицами                 | Отвечает за                                                       |
| ------------- | --------------------------------- | ----------------------------------------------------------------- |
| auth          | `sessions`, `auth_tokens`         | регистрация, вход/выход, подтверждение email, сброс пароля, guard |
| users         | `users`                           | профиль пользователя                                              |
| specialists   | `specialist_profiles`             | профиль и настройки бронирования                                  |
| services      | `services`                        | услуги, архивирование                                             |
| scheduling    | `weekly_availability`, `days_off` | расписание и выходные                                             |
| bookings      | `bookings`                        | слоты, создание и смена статусов броней, истечение pending        |
| notifications | `outbox_messages`                 | запись в outbox, обработчик, отправка писем                       |

Правила зависимостей:

1. **Таблицу пишет и читает только модуль-владелец.** Другим модулям данные доступны только через его экспортированный сервис.
2. **Граф зависимостей ацикличен.** `forwardRef` запрещён: цикл означает ошибку в границах модулей.
3. **Стрелка идёт от зависимого по смыслу к самостоятельному.** Бронь не существует без расписания, расписание существует без броней → `bookings → scheduling`.
4. **Слоты — use case модуля bookings.** «Куда можно забронировать» — вопрос о бронировании; расписание — входные данные. Расчёт — чистая функция `calculateSlots(rules, daysOff, busy, settings, now)` в `bookings/domain`.
5. **notifications не обращается к другим модулям.** Всё, что нужно для письма, кладётся в `payload` сообщения outbox в момент события (снимок, как и сама бронь).

Соблюдение правил 1–2 и правил слоёв из §1 проверяет dependency-cruiser в `pnpm lint` ([ADR-011](../adr/011-architecture-checks-and-git-hooks.md)). Граф выше повторён объектом `moduleDependencies` в `apps/api/.dependency-cruiser.cjs`: новое ребро — правка конфигурации и этого документа в одном изменении.

## 3. Структура директорий

```
apps/api/src/
  main.ts
  app.module.ts
  infrastructure/
    database/        провайдер Drizzle, схема, тип Tx
    config/          типизированная конфигурация из env
    logging/
    health/
  modules/
    auth/
      auth.module.ts
      auth.controller.ts
      auth.service.ts
      session.guard.ts
      sessions.repository.ts
      auth-tokens.repository.ts
      domain/
      dto/
    bookings/
      bookings.module.ts
      bookings.controller.ts
      slots.controller.ts
      bookings.service.ts
      slots.service.ts
      bookings.repository.ts
      domain/
        booking-status.ts      машина состояний, эффективный статус
        calculate-slots.ts
        errors.ts
      dto/
    ...остальные модули по тому же образцу
```

Схема Drizzle — по файлу на модуль-владельца (`modules/*/…schema.ts`), собирается в `infrastructure/database`. Миграции — `apps/api/drizzle/`.

## 4. Фоновые задачи

- Обработчик outbox, истечение `pending`, уборка истёкших сессий и токенов — **в том же процессе** через планировщик NestJS.
- Выборка работы — `SELECT ... FOR UPDATE SKIP LOCKED`: если экземпляров backend станет несколько, они не возьмут одно и то же сообщение. Безопасно с первого дня, без отдельного брокера.
- Вынос в отдельный процесс — когда фоновая работа начнёт мешать latency API.

## 5. Ошибки

Домен и сервисы бросают **доменные ошибки** (например, `BookingConflictError`, `InvalidStatusTransitionError`, `NotFoundError`) без знания об HTTP. Перевод в HTTP-ответы — в одном месте (решение 6: контракты API и ошибки).
