# Архитектура frontend (apps/web)

> Статус: утверждена 2026-11-09. Решение: [ADR-009](../adr/009-frontend-structure.md).
> Описаны только точки стыковки с архитектурой системы; приёмы вёрстки и компонентов — на усмотрение реализации.

## 1. Маршруты

```
app/
  (public)/
    page.tsx                     лендинг
    book/[slug]/page.tsx         публичная страница специалиста и выбор слота
  (auth)/
    login/  register/  verify-email/  reset-password/
  (app)/                         только для вошедших; layout проверяет GET /me
    bookings/                    мои брони как клиента
    specialist/
      bookings/  services/  schedule/  settings/
```

Публичная страница — под префиксом `/book/{slug}`: новые маршруты приложения не конфликтуют со slug специалистов.

## 2. Данные

| Сценарий                                                          | Механизм                                                                                                         |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Начальная загрузка страниц                                        | Server Components → серверный клиент API (`API_INTERNAL_URL`, cookie пользователя пробрасывается из `cookies()`) |
| Интерактивные данные (слоты при смене дат, списки после действий) | TanStack Query + openapi-fetch через `/api/*`                                                                    |
| Изменения                                                         | только из браузера через `/api/*` (openapi-fetch); затем инвалидация запросов или `router.refresh()`             |

- **Server Actions не используются для изменений.** Единственный путь изменения данных — браузер → `/api/*` → API. Так CSRF-проверка `Origin`, cookie и формат ошибок одинаковы для всех изменений (ADR-005, ADR-007).
- Глобального стора нет: серверное состояние — TanStack Query, локальное — компоненты.
- `QueryClient` создаётся в `app/providers.tsx` внутри `useState`: один на вкладку браузера и никогда не общий для разных запросов на сервере. Слоты: `staleTime` 30 секунд, перезагрузка при возврате на вкладку, предыдущая неделя остаётся на экране, пока грузится следующая (`keepPreviousData`).

## 3. Аутентификация

- `proxy.ts` (Next.js 16): оптимистичный редирект на `/login`, если нет cookie сессии. Сессию не проверяет — это не граница безопасности.
- Layout `(app)` на сервере вызывает `GET /me`; 401 → редирект на вход. Так обрабатывается и устаревшая cookie, которую `proxy.ts` пропускает.
- Источник истины о сессии и правах — API.
- `getCurrentUser` и `getMySpecialistProfile` обёрнуты в `cache()` React: layout и страница спрашивают оба, API вызывается один раз за запрос.
- **Куда после входа** — серверная страница `/start` (запасной адрес `safeRedirectPath`): `?next=` → туда; не специалист → «Мои записи»; специалист без расписания → «Расписание» (без него нет слотов); специалист с расписанием → «Мои записи», вкладка «Ко мне» (заявки истекают через 24 часа).
- «Мои записи» (`features/my-bookings`): вкладки «Ко мне» (только специалисту) и «Мои», «Предстоящие» и «Прошедшие». У специалиста в предстоящих сначала «Ждут ответа» (`pending`), затем «Подтверждённые»; отклонённые и отменённые будущие брони он не видит до их времени — об отмене приходит письмо. Кнопки — по `allowedActions`; `BOOKING_STATUS_CHANGED` и `CANCEL_DEADLINE_PASSED` → сообщение и обновление страницы.
- Серверный клиент (`shared/api/server-client.ts`, `server-only`) пробрасывает в API cookie и `X-Forwarded-For` входящего запроса.
- Параметр `?next=` после входа принимается только как путь своего сайта (`shared/lib/safe-redirect.ts`) — иначе страница входа стала бы открытым редиректом для фишинга.

## 4. Бизнес-правила не дублируются

Frontend не реализует бизнес-правила; он отображает решения API.

- Ответ с бронью содержит `allowedActions: ("cancel" | "confirm" | "reject")[]` — действия, доступные **текущему пользователю** сейчас. Вычисляется той же доменной функцией, что проверяет действие в use case. Кнопки показываются по этому списку.
- Для пояснений API отдаёт данные, а не правила: например, `cancelDeadlineAt` («отменить можно до 14:00»).
- Список — снимок на момент ответа: пока страница открыта, дедлайн может пройти. API всё равно проверяет действие и вернёт 422 `CANCEL_DEADLINE_PASSED`; UI показывает сообщение и обновляет данные.
- Слоты frontend не вычисляет — получает от `GET /specialists/{slug}/slots`.
- Валидация форм — только для UX.

## 5. Ошибки

- `shared/api/errors.ts` — единое место обработки по `code`: известные коды → поведение UI (например, `BOOKING_SLOT_TAKEN` → сообщение и перезагрузка слотов, `BOOKING_STATUS_CHANGED` → обновление брони); неизвестные → `detail` из Problem Details.
- Ошибки валидации раскладываются по полям формы через `errors[].path`.
- `hasCode(error, ...codes)` — проверка кода. `SLOT_GONE_CODES` (`BOOKING_SLOT_TAKEN`, `SLOT_NOT_AVAILABLE`): выбранный слот пропал — сообщение, сброс выбора и перезагрузка слотов, без повтора запроса.
- Кнопка «Записаться» блокируется на время запроса: двойной клик не отправляет две заявки.
- `requestId` показывается в сообщении о непредвиденной ошибке («код обращения»), чтобы найти запрос в логах.

## 6. Время

- Сервер не знает пояс браузера, поэтому:
  - публичная страница: сетка слотов рендерится на клиенте в поясе браузера (`Intl.DateTimeFormat`) с явной подписью пояса. Неделя — семь местных полуночей браузера (`new Date(y, m, d + i)`), в API уходят их моменты `[from, to)`; слоты группируются по дате браузера (`features/booking/lib/slot-grid.ts`). Пока пояс неизвестен (SSR), вместо сетки — «Загружаем свободное время…»;
  - кабинет: SSR в `user.timezone` из профиля.
- Все форматирования времени — в `shared/lib/time.ts` (с явным поясом: сервер и браузер выводят одно и то же). Кабинет показывает время в поясе из профиля с подписью пояса.
- Пояс браузера читается только на клиенте (`useBrowserTimeZone`, `useSyncExternalStore` с `null` на сервере): чтение во время SSR дало бы HTML, не совпадающий с клиентом.

## 7. Структура кода

```
apps/web/src/
  app/                маршруты — тонкие, собирают фичи
  features/
    auth/  booking/  schedule/  services/  specialist-profile/
      components/  hooks/  api.ts
  shared/
    api/              серверный и браузерный клиенты, сгенерированные типы, errors.ts
    ui/               дизайн-система (shadcn/ui на Tailwind)
    lib/              время, форматирование
```

- Фичи не импортируют друг друга напрямую; общее — в `shared`. Проверяется dependency-cruiser в `pnpm lint` (`apps/web/.dependency-cruiser.cjs`, [ADR-011](../adr/011-architecture-checks-and-git-hooks.md)).
- Формы — react-hook-form + Zod.
- Тексты интерфейса — на русском, собраны в одном месте в рамках фичи (готовность к i18n без самой i18n).
- Страницы подтверждения email и сброса пароля читают токен из `location.hash` (ADR-008) через `useFragmentToken`: токен сразу убирается из адресной строки и истории, на страницах `Referrer-Policy: no-referrer`. Подтверждение отправляется один раз даже при двойном запуске эффектов в Strict Mode.
- Значения форм, которые влияют на серверный HTML (например, выбранный `<option>`), передаются в `defaultValue`: `register()` react-hook-form выставляет значение только после hydration.
